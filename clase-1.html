Un método que cambia al objeto

class Auto:
    def __init__(self, marca):
        self.marca = marca
        self.velocidad = 0

    def acelerar(self):
        self.velocidad = self.velocidad + 20
print(auto_1.velocidad)  # 0

auto_1.acelerar()
auto_1.acelerar()

print(auto_1.velocidad)  # 40

¿Quién cambió la velocidad?

El auto se cambió a sí mismo. Nadie tocó el dato desde afuera.

En pantalla
Por primera vez un método modifica un atributo. Es la lámina que justifica todo el paradigma.
Preguntá
“¿Cuánto va a imprimir el segundo print? Piénsenlo antes de que lo revele.”
Respuesta esperada

Revelá cuando
Arriesgaron un número. Después preguntá lo importante: “¿quién cambió la velocidad?”
Idea clave
Acá se cobra la promesa del principio: los datos y las funciones están juntos porque las funciones trabajan sobre esos datos. Si acelerar() viviera afuera, habría que pasarle el auto.

Volvemos sobre self, ahora con dos autos

¿Quién es self cada vez?

def encender(self):
    print("Encendido", self.marca)


auto_1.encender()  # self = auto_1
auto_2.encender()  # self = auto_2

self quiere decir “este objeto”: el que está usando el método justo ahora.

Es cómo el auto se refiere a sí mismo. Nada más que eso.

🔐 Encapsulación · así se ve en código 
class Jugador:
    def __init__(self, nombre):
        self.nombre = nombre
        self.vida = 100

    def recibir_daño(self, cantidad):
        self.vida = self.vida - cantidad
        if self.vida < 0:
            self.vida = 0   # nunca menos de 0
jugador.recibir_daño(30)
print(jugador.vida)   # 70

jugador.recibir_daño(500)
print(jugador.vida)   # 0, no -430

Ahí está el candado

El if es la única razón por la que la vida no queda en negativo. Ese control vive adentro del objeto.

En pantalla
El método controlado que reemplaza a jugador.vida = -999999 de la actividad anterior.
Preguntá
“Le pego 500 de daño a alguien con 100 de vida. ¿Cuánta vida le queda?”
Respuesta esperada
Van a decir −400. Dejalos. Después mostrales que da 0, por el if.
Revelá cuando
Dijeron el número negativo. El contraste es lo que enseña.
Idea clave
Encapsular no es esconder: es que el dato solo se pueda cambiar pasando por un control. Sacá el if y el pilar desaparece.

Contá los if

Cero. El for no sabe ni le importa quién es cada uno. Cada objeto sabe responder.

En pantalla
El mismo nombre de método, escrito tres veces de tres maneras. Es literalmente “muchas formas”.
Preguntá
“¿Cuántos if tuve que escribir para que cada uno haga su sonido?”

Van a buscarlos. No hay ninguno. Ese descubrimiento es el pilar.
Revelá cuando
Se den cuenta de que no hay if. Si no lo ven, preguntá: “¿y si mañana agrego una Vaca? ¿qué toco de este for?” → Nada.
Idea clave
Sin polimorfismo, ese for sería una cadena de if tipo == "perro" … elif tipo == "gato"… que crece con cada animal nuevo.
Conectá
Las tres clases heredan de Animal: sin herencia, no habría polimorfismo. Los pilares se usan juntos.

En pantalla
Opcional de verdad: decíselo. El que no lo hace no queda atrás.
Por qué este ejercicio
Junta todo lo de hoy en 10 líneas: __init__, self, un método que modifica un atributo, y el if que impide el valor imposible. Es el recibir_daño() de la clase, con otro disfraz.
La trampa buena
El punto 3 pide jugar 6 veces: 6 × 20 = 120, más que la energía inicial. Si no pusieron el if, les va a dar energía negativa. Ahí se dan cuenta solos de para qué servía encapsular.
Revelá cuando
Al final, para que se lleven la sensación de que hoy aprendieron bastante más de lo que creen.
