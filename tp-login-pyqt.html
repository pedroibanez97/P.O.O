01

Entender qué vamos a construir

Antes de abrir cualquier programa: qué se ve, qué se toca y qué pasa

Nivel 1

El problema

Una persona abre tu programa. Si ya tiene cuenta, entra. Si no, se registra. ¿Qué tiene que ver, qué puede tocar y qué pasa cada vez que toca algo?

Dos pantallas, una aplicación

Login
  • Usuario o correo electrónico.
  • Contraseña, oculta mientras se escribe.
  • Opción para mostrar u ocultar la contraseña.
  • Botón para iniciar sesión.
  • Acceso a la pantalla de registro.
  • Un lugar para los mensajes de validación.
Registro
  • Nombre y apellido.
  • Usuario o correo electrónico.
  • Contraseña y confirmación de la contraseña.
  • Botón para registrarse.
  • Acceso para volver al login.
  • Un lugar para los mensajes de validación.

Cómo se pasa de una a otra

Login

Iniciar sesión → revisa los datos → muestra un mensaje.

«Registrate» → btn_ir_registro btn_volver_login ← «Volver»

Registro

Crear cuenta → revisa los datos → guarda (simulado) → muestra un mensaje.

Pensá · antes de diseñar nada

1. ¿Qué información necesita cada pantalla para hacer su trabajo?

2. ¿Qué elementos son solamente visuales (se ven, pero no hacen nada)?

3. ¿Qué elementos requieren programación?

4. ¿Qué debería ocurrir cuando se presiona cada botón? Uno por uno.

5. ¿Qué responsabilidades pertenecen a la interfaz y cuáles a la lógica?

Probá · clasificá cada cosa

Marcá dónde va a vivir cada una. Algunas tienen trampa: leelas despacio.

▸ Pista (abrila después de marcar)

Hacete una sola pregunta por fila: ¿esto describe cómo es la pantalla al abrirse, o decide qué pasa cuando alguien hace algo? Lo primero va en el .ui. Lo segundo, en Python. La trampa está en las filas 2 y 3: el estado inicial (puntos) es diseño; el cambio al tildar es comportamiento. Lo mismo con el mensaje: el lugar es diseño, el texto que aparece lo decide el código.

La idea

La interfaz describe
  • Qué widgets hay y dónde.
  • Cómo se llaman (objectName).
  • Cómo arrancan: textos, campos ocultos, orden del Tab.
  • Cómo se ven.
La lógica decide
  • Qué pasa cuando se toca cada cosa.
  • Qué datos son válidos.
  • Qué mensaje mostrar.
  • A qué pantalla ir. Quién puede entrar.

02

Preparar el entorno

Una carpeta, un entorno virtual, una librería y una herramienta

Nivel 1

El problema

PyQt no viene con Python. Qt Designer tampoco. Y tener uno no te da el otro.

La idea

PyQt6 · una librería

Código que tu programa importa. Sin ella, from PyQt6 import uic falla. Quien ejecute tu aplicación la necesita: por eso va en requirements.txt.

Qt Designer · una herramienta

Un programa aparte, con ventanas, para dibujar pantallas. Guarda archivos .ui. Tu aplicación no lo necesita para ejecutarse: solo vos, mientras diseñás.

¿Por qué sirve un Designer «de PySide6» para PyQt6?

PyQt6 y PySide6 son dos puentes distintos hacia la misma biblioteca: Qt, escrita en C++. El .ui es un formato de Qt, no de PyQt. Designer lo escribe; PyQt6 lo lee. Instalamos PySide6-Essentials únicamente porque trae Designer listo para abrir con un comando, en Windows y en Mac.

¿Y para qué un entorno virtual?

Un entorno virtual (.venv) es una carpeta con su propio Python y sus propias librerías, solo para este proyecto. Lo que instales ahí no rompe otros proyectos, y lo que necesita este proyecto queda anotado en requirements.txt para que cualquiera lo reconstruya. La carpeta .venv no se sube a Git: se vuelve a crear.

Paso a paso

1 · PythonComprobá la versión. Necesitás Python 3.10 o más nuevo.
Windows: py --version (si no anda, python --version) · Mac: python3 --version
2 · CarpetaCreá la carpeta del proyecto y entrá en ella. Desde acá, todos los comandos se ejecutan parados en esta carpeta.
mkdir login-registro y después cd login-registro
3 · EntornoCreá el entorno virtual.
Windows: py -m venv .venv · Mac: python3 -m venv .venv
4 · ActivarActivalo. Se hace en cada terminal nueva; la señal de que funcionó es que la línea empieza con (.venv).
Windows, PowerShell: .venv\Scripts\Activate.ps1 · Windows, CMD: .venv\Scripts\activate.bat
Mac (zsh o bash): source .venv/bin/activate
5 · InstalarCon el entorno activo, el comando es igual en los dos sistemas (adentro del entorno, python ya apunta al Python correcto):
python -m pip install --upgrade pip
python -m pip install PyQt6 PySide6-Essentials
Son unos 200 MB: con el Wi-Fi del aula puede tardar.
6 · DesignerAbrilo con pyside6-designer (con el entorno activo). La primera vez puede tardar unos segundos. Tiene que aparecer el diálogo New Form.
7 · PyQtComprobá que PyQt6 se importa: python -c "from PyQt6 import uic; print('PyQt6 OK')"
Mac con chip Apple (M1, M2, M3, M4)

Los paquetes de PyQt6 y PySide6 son universales: corren nativos, sin Rosetta. No hace falta Homebrew ni descargar nada de qt.io, y no busques Designer en Aplicaciones: vive adentro de tu .venv y se abre con pyside6-designer. Si una guía de internet te da una ruta tipo /Applications/Qt/… o /usr/local/…, no es la tuya.

Alternativa, solo si lo anterior no funciona en tu compu

Si no podés instalar con pip (por ejemplo, en una computadora del laboratorio sin permisos), instalá Qt Creator con el instalador oficial de código abierto de Qt (qt.io). Trae Designer integrado: abrís el .ui y se edita en el modo Design. Es una descarga bastante más grande y pide crear una cuenta de Qt.

La ventana de prueba

Probá · que VS Code use tu entorno

Abrí la carpeta login-registro en VS Code. Cmd/Ctrl + Shift + P → «Python: Select Interpreter» → elegí el que dice .venv. Si te salteás este paso, el botón ▶ de VS Code ejecuta con otro Python y vas a ver ModuleNotFoundError: No module named 'PyQt6' aunque lo hayas instalado.

03

Aprender Qt Designer explorando

Construir las dos pantallas sin escribir todavía una línea de lógica

Nivel 1

El problema

En la guía de PyQt cada widget era una línea de código, cada posición una cuenta, y para ver cómo quedaba había que ejecutar. Con diez widgets y dos pantallas, diseñar así es lento y se rompe con cualquier cambio.

La idea

Qué es un archivo .ui

Una descripción de la pantalla, en texto (formato XML): qué widgets hay, cómo se llama cada uno, qué propiedades tiene y cómo están organizados. Designer lo escribe mientras dibujás. No contiene comportamiento: no dice qué pasa cuando hacés clic.

Las cinco zonas de Designer

ZonaQué esQué problema resuelve
1 · Widget BoxEl catálogo de piezas, por categoría.No tenés que recordar el nombre de cada clase: lo arrastrás al formulario.
2 · FormularioLa pantalla que estás diseñando.Ves el resultado mientras lo construís, sin ejecutar nada.
3 · Object InspectorEl árbol de quién está adentro de quién, con su nombre y su clase.Seleccionar widgets aunque estén tapados, y ver si alguno quedó fuera de un layout.
4 · Property EditorTodas las propiedades del widget seleccionado.Configurar nombre, texto, tamaños y modos sin escribir código.
5 · Barra de layoutsBotones para organizar: vertical, horizontal, grilla, romper layout.Que las posiciones se calculen solas, como en la sección 7 de la guía de PyQt.
Mirá bien el Property Editor

Las propiedades están agrupadas en bloques: QObject, QWidget, QAbstractButton, QPushButton. Cada bloque es una clase padre. Un botón tiene objectName porque es un QObject, y tiene text porque es un QAbstractButton. Es la herencia de la clase 2, a la vista.

Los nombres que usa toda la guía

El código de las etapas siguientes depende de estos objectName. Si cambiás uno, tenés que cambiarlo también en Python: elegí respetarlos. La convención es prefijo según el tipo + qué es, en minúscula y con guion bajo.

La demostración · login.ui, paso a paso

1 · NuevoFile → New… → plantilla Widget → Create. No elijas Main Window: trae barra de menú y de estado que no vamos a usar, y no encaja con la clase que vamos a escribir (en la etapa 5 vas a ver el error que produce).
2 · GuardarGuardalo ya, vacío: File → Save As → entrá a login-registro, creá la carpeta ventanas y guardá como login.ui. Guardar al principio evita el clásico «lo guardé en Descargas». Después, Cmd/Ctrl + S seguido.
3 · NombreCon el fondo del formulario seleccionado, en el Property Editor cambiá objectName a pantalla_login.
4 · TarjetaArrastrá un Frame (en Containers) al centro del formulario. Nombralo frame_tarjeta. Todo lo demás va a vivir adentro de este frame.
5 · WidgetsSoltá dentro del frame, más o menos en columna: un Label (título), un Label y un Line Edit (usuario), un Label y un Line Edit (contraseña), un Check Box, un Push Button, un Label (mensaje) y otro Push Button (ir a registro). No importa que queden torcidos: el layout los va a alinear.
6 · TextosDoble clic sobre cada widget para escribir su texto visible. Al Label del mensaje borrale el texto (TextLabel): empieza vacío y lo llena Python.
7 · NombresUno por uno, poné los objectName de la tabla. Revisalos en el Object Inspector.
8 · Layout adentroClic derecho en una zona vacía del frame → Lay out → Lay Out Vertically. Todo queda en columna.
9 · CentrarArrastrá cuatro espaciadores alrededor de la tarjeta: Vertical Spacer arriba y abajo, Horizontal Spacer a izquierda y derecha. Clic en el fondo del formulario → Lay out → Lay Out in a Grid. Los espaciadores empujan desde los cuatro lados y la tarjeta queda en el centro.
10 · ContraseñaSeleccioná input_password → propiedad echoMode → Password. De paso, completá placeholderText en los dos campos (el texto gris de ayuda).
11 · TamañosEn frame_tarjeta: maximumSize → ancho 400, y minimumSize → ancho 360. Así, con la ventana maximizada, la tarjeta no se estira de punta a punta.
12 · TabEdit → Edit Tab Order: hacé clic en los widgets en el orden en que una persona los recorre. Esc para salir.
13 · PreviewForm → Preview (Ctrl + R en Windows, Cmd + R en Mac). Es tu pantalla funcionando, sin Python: escribí, apretá Tab, agrandá y achicá la ventana.
¿Por qué una grilla y no un layout vertical?

Un layout vertical sobre el formulario centra la tarjeta de arriba a abajo, pero no de izquierda a derecha: con ancho máximo, la tarjeta queda pegada a un costado. Lo comprobamos al preparar esta guía. Con la grilla y los cuatro espaciadores se resuelven las dos direcciones a la vez, sin tocar código.

04

De .ui a Python

Que tu programa lea el diseño y lo convierta en una ventana de verdad

Nivel 1

El problema

Tenés un login.ui impecable. Python no sabe que existe.

La idea

login.uitexto: qué widgets hay y cómo se llaman
▼uic.loadUi() lo lee mientras el programa corre
objetos de PyQt6 en memoriaun QPushButton por cada <widget class="QPushButton">
▼cada objectName se vuelve un atributo
ventana.btn_login · ventana.input_usuario …

La demostración

Línea por línea

QApplicationLa aplicación. Va antes que cualquier widget y hay una sola por programa. Sin ella: QWidget: Must construct a QApplication before a QWidget, y el programa se cierra.
uic.loadUi()Abre el .ui, lee el XML y crea todos los widgets con sus propiedades y layouts. Devuelve el widget raíz: el formulario.
ventanaEse widget raíz. Probá type(ventana): es un QWidget común, porque elegiste la plantilla Widget.
show()Crear no es mostrar. Sin show() la ventana existe en memoria y nadie la ve. No da error: simplemente no aparece nada.
app.exec()Arranca el bucle de eventos y no termina hasta que cerrás la ventana. sys.exit() le pasa al sistema operativo el código con el que terminó.

El bucle de eventos

Espera

No hace nada. Espera a que pase algo.

Evento

Un clic, una tecla, la ventana que cambia de tamaño.

Responde

Le avisa al widget, y si conectaste un método, lo ejecuta.

Redibuja

Actualiza lo que cambió en pantalla.

↺ vuelve a esperar · así hasta que cerrás la ventana · recién ahí exec() termina

Es la misma idea del while del menú de Arena de Combate, pero ya escrito por Qt. Por eso un programa con interfaz no «termina» después de la última línea: se queda dando vueltas acá adentro.

Acceder a los widgets por su nombre

La ruta del archivo

Probá · rompelo a propósito

Salí de la carpeta del proyecto (cd ..) y ejecutá python login-registro/prueba_ui.py. Leé lo que aparece.

  1. Un traceback se lee de abajo hacia arriba. La última línea dice qué pasó: el tipo de error y el mensaje.
  2. No te quedes con la primera mitad del mensaje. «invalid Qt Designer file» confunde: el archivo no es inválido, no existe en esa ruta. La causa real está al final: No such file or directory.
  3. Las líneas File … dicen dónde. Buscá la primera que sea un archivo tuyo (la resaltada): ahí está la línea que lo provocó. Las de adentro de .venv son de la librería; casi nunca el problema está ahí.

El problema

La idea

Una pantalla es un objeto

El problema

Hay cinco cosas que una persona puede tocar y cada una necesita una respuesta. Si las conectás todas juntas y algo falla, no vas a saber cuál fue.

La idea · señales y slots

self.btn_login.clicked.connect(self.iniciar_sesion)
  1. self.btn_loginEl emisor: el botón que creó loadUi a partir del objectName.
  2. .clickedLa señal: algo que puede pasar. No pasa ahora; puede pasar en cualquier momento.
  3. .connect( … )La conexión: «cuando pase, avisale a…». Se hace una sola vez, en el __init__.
  4. self.iniciar_sesionEl slot: el método que responde. Sin paréntesis: lo entregás, no lo ejecutás.
El error más común, otra vez

Con connect(self.iniciar_sesion()) Python ejecuta el método en ese momento —al abrir la ventana— y le pasa a connect lo que devolvió: None. El resultado: TypeError: argument 1 has unexpected type 'NoneType'. Si ves NoneType en un error de connect, buscá paréntesis de más.

Autenticación

Usuarios en memoria. No es un sistema real: se borra al cerrar.

El problema

Para que el login tenga sentido, alguien tiene que acordarse de quién se registró. Todavía no hay base de datos.

La idea · un servicio que no sabe que existe una ventana

ServicioAutenticacion

Una clase en controladores/autenticacion.py con dos responsabilidades: registrar y autenticar. Guarda los usuarios en un diccionario. No importa nada de PyQt: no sabe que hay pantallas. Es la misma idea que BasededatosControlador en la guía de MySQL: un lugar, una responsabilidad.

Ni siquiera en una simulación: contraseñas en texto plano

Aunque esto viva en memoria, no guardamos la contraseña. Guardamos un hash con sal: el resultado de una cuenta que no se puede deshacer. Para verificar, se repite la cuenta con lo que escribió la persona y se comparan los resultados. Así, quien mire los datos —vos, un compañero, alguien que los robe— no ve ninguna contraseña. Y como la gente repite contraseñas, filtrar una no compromete sus otras cuentas.

"clave segura 1"lo que escribió la persona
▼+ sal: 16 bytes al azar, distintos para cada usuario
PBKDF2-SHA256 · 600.000 vueltaslento a propósito: adivinar cuesta caro
▼
b'\x8f\x1c\xe2…'esto es lo único que se guarda (junto con la sal)

▸ Pista para autenticar()

Tres pasos: buscá al usuario en self._usuarios con .get() (si no está, devolvé False); calculá el hash de la contraseña que te pasaron usando la sal guardada de ese usuario; comparalo con el hash guardado usando hmac.compare_digest(a, b), que compara sin delatar —por el tiempo que tarda— cuántos bytes coinciden.

Secretos y Git

Si una contraseña llegó a un commit, borrarla en el commit siguiente no alcanza: queda en el historial, y el historial se sube entero. Lo correcto es cambiar esa contraseña. Por eso lo sensible va en .env desde el principio, y el .env en el .gitignore, como en la guía de MySQL.

¿Y si... agregamos «Recordar mi usuario»?

Una casilla en el login. Al volver a abrir la app, el usuario ya aparece escrito.

▸ Pistas

Investigá QSettings: guarda valores chicos entre una ejecución y otra, en el lugar que corresponde a cada sistema operativo. Mirá setValue() y value(). ¿Dónde los guarda en Windows y dónde en Mac?

Se recuerda el usuario. La contraseña, jamás.

¿Y si... mostramos la fortaleza de la contraseña?

Mientras se escribe en el registro, un indicador dice si es débil, aceptable o fuerte.

▸ Pistas

¿Qué señal de QLineEdit avisa cada vez que cambia el texto? Conectala a un método que calcule un puntaje y lo muestre en un QLabel o un QProgressBar.

Para el puntaje: largo, si tiene números (any(c.isdigit() for c in texto)), mayúsculas, símbolos. ¿Dónde va ese cálculo: en la ventana o en el servicio? ¿Por qué?

Pensá: un medidor orienta, no garantiza nada. ¿Es más fuerte Ab1! o caballo correcto batería grapa?

¿Y si... agregamos una pantalla para recuperar la contraseña?

Un enlace «¿Olvidaste tu contraseña?» que lleva a una tercera pantalla.

▸ Pistas

Es un .ui más, una clase más y un addWidget más en VentanaPrincipal. Si tuviste que tocar las otras dos pantallas para agregarla, algo de la organización se puede mejorar.

Pensá qué haría falta de verdad: un correo, un código de un solo uso, que venza. Acá no simules que se envía un mail. Y fijate el mensaje: «Si el usuario existe, te enviaremos instrucciones» no revela quién está registrado. ¿Por qué importa?

¿Y si... necesitamos registrar los datos en MySQL?

Que los usuarios sigan ahí al cerrar la app.

▸ Pistas

Volvé a las secciones 8, 9 y 11 de la guía de Python + MySQL. Pensá una tabla usuarios: ¿qué columnas necesita? ¿Cuál tiene que ser única? ¿Dónde van la sal y el hash? (Investigá VARBINARY, o convertí los bytes con .hex().)

La pregunta que importa: ¿cuántos archivos tuviste que tocar? Si las ventanas cambiaron, la separación no estaba bien hecha. Solo debería cambiar el interior de ServicioAutenticacion.

Todas las consultas con %s. Y los datos de conexión, en el .env.

¿Y si... varias pantallas necesitan la misma lógica de autenticación?

Después del login aparece una pantalla «Mi perfil» que necesita el servicio y saber quién inició sesión.

▸ Pistas

¿Quién crea el servicio? ¿Quién se lo pasa a la pantalla nueva? ¿Qué pasaría si la pantalla nueva creara el suyo? (Ya lo viviste en la etapa 8.)

¿Cómo se entera VentanaPrincipal de que el login salió bien, sin meterse en los botones del login? Investigá pyqtSignal: una pantalla puede emitir su propia señal («sesión iniciada», con el usuario) y la ventana principal conectarse a ella. Con eso también podés resolver el «Pensá» de la etapa 6.

La prueba de que lo hiciste bien

Si cuando llegue la base de datos tenés que tocar las ventanas, la separación no estaba bien hecha. Es la misma frase con la que cerraba la guía de MySQL, ahora vista desde el otro lado: la interfaz no tiene por qué saber cómo se guardan los usuarios. Solo pide.

Lo que todavía falta para un sistema real (y está bien que falte)
  • Persistencia: que los usuarios sobrevivan al programa.
  • Límite de intentos y bloqueo temporal ante muchos errores seguidos.
  • Sesiones: recordar quién entró, por cuánto tiempo, y poder cerrar sesión.
  • Verificar el correo y recuperar la contraseña con enlaces que vencen.
  • Roles y permisos: no todos pueden hacer lo mismo.
  • Si la app habla con un servidor: conexión cifrada y validación del lado del servidor.

Antes de cerrar la guía
  1. Instalar PyQt6 te da una librería; instalar Designer te da una herramienta. El .ui es el puente entre las dos.
  2. El .ui describe; Python decide. Lo único que comparten es el objectName.
  3. uic.loadUi(ruta, self) convierte el diseño en atributos de tu objeto. Por eso la pantalla hereda de QWidget.
  4. Señal → slot: widget.señal.connect(self.metodo), sin paréntesis.
  5. Leer, validar, cortar o seguir. Validar ayuda a la persona; no reemplaza al servidor ni a la autenticación.
  6. Una contraseña nunca se guarda: se guarda su hash con sal. Y una simulación se presenta como simulación.
  7. Cada archivo sabe una cosa y no sabe las demás. Así, cuando llegue MySQL, cambia un solo lugar.

Diseñamos visualmente, programamos el comportamiento y conectamos ambas partes con buenas prácticas.

Si al terminar podés abrir Designer, cambiar una pantalla y saber exactamente qué parte del código se ve afectada —y cuál no—, el trabajo práctico cumplió su objetivo.
