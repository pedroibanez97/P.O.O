01

El punto de partida

Dos mundos que todavía no se hablan

Sabemos escribir SQL. Sabemos programar en Python.
¿Cómo hacemos para que Python ejecute una consulta SQL sobre nuestra base?

Hasta hoy, esos dos mundos vivieron separados. El SQL lo escribiste en Workbench, en phpMyAdmin o en la consola de MySQL: escribías la consulta a mano y mirabas el resultado en pantalla. Python, mientras tanto, guardaba todo en listas y diccionarios que desaparecían al cerrar el programa.

Lo que buscamos

Un puente: algo que lleve una consulta escrita en Python hasta MySQL, y traiga el resultado de vuelta convertido en datos que Python entienda.

02

El conector

La librería que hace de puente

Qué es un conector

Un conector (o driver) es una librería que sabe hablar el idioma de un motor de base de datos. Traduce: recibe de Python un texto con una consulta, se lo manda a MySQL por la red, espera la respuesta y te la devuelve como listas y tuplas de Python.

Se instala igual que cualquier librería

Y se importa casi igual

Un detalle que confunde a todos

Lo que instalás 
mysql-connector-python

Así se llama el paquete en PyPI, el repositorio de donde pip lo baja.

Lo que importás 
import mysql.connector

Así se llama el módulo adentro de Python. El punto indica que connector vive dentro de mysql.

No tienen por qué coincidir, y muchas veces no coinciden. Es normal, y es una de las primeras cosas que se buscan en la documentación de cualquier librería nueva.

Comparalo con lo que ya conocés

Librería¿Se instala?¿Qué te da?
randomNo, viene con PythonNúmeros al azar. No sale de tu programa.
tkinterNo, viene con PythonVentanas. Habla con tu sistema operativo.
pygameSí, con pipUn videojuego. Habla con pantalla, teclado y sonido.
mysql.connectorSí, con pipHabla con otro programa: el servidor MySQL.
Investigá

Existen otros conectores para MySQL (PyMySQL, mysqlclient) y conectores para otros motores (psycopg2 para PostgreSQL, sqlite3 que viene incluido en Python). Buscá uno y contestá: ¿el código se parece al nuestro? Vas a descubrir que sí, y eso no es casualidad.

Antes de seguir

Necesitás MySQL corriendo en tu computadora (XAMPP, MAMP, Workbench o el servidor solo) y una base creada. Si pip install salió bien pero después nada conecta, el problema casi nunca es Python: es que el servidor está apagado.

¿Y qué pasa si la conexión falla?

Con el código de arriba, el programa explota: aparece un Traceback rojo y todo se corta ahí. Para un ejercicio da igual; para una aplicación que alguien va a usar, no. Queremos enterarnos del problema sin morir en el intento.

Error clásico

Access denied for user 'root'@'localhost' → usuario o contraseña mal.
Can't connect to MySQL server → el servidor está apagado o el puerto no es ese.
Unknown database 'tienda' → conectaste bien, pero esa base no existe todavía.
Leer el error es la mitad del trabajo: cada mensaje te dice exactamente dónde mirar.

Ejecutar una consulta

Conectarse no alcanza: hay que preguntar algo

Estar conectado es como tener la llamada establecida: todavía nadie dijo nada. Para hablar necesitamos un cursor.

Cursor

El cursor es el objeto que lleva y trae. Vos le pasás la consulta, él la manda a MySQL, y después se queda con el resultado hasta que se lo pedís. Pensalo como el mozo: la conexión es estar sentado en el restaurante; el cursor es quien lleva tu pedido a la cocina y vuelve con el plato.

fetchall() o fetchone()

fetchall() 
[(1, 'Remera'), (2, 'Buzo')]

Trae todas las filas, siempre en una lista. Si no hay nada, la lista viene vacía: [].

05

Consultas con parámetros

Cuando la consulta depende de lo que escribe el usuario

¿Y si quiero buscar un producto en particular, el que el usuario escriba?

La consulta ya no es fija: una parte la pone el programa y otra parte la pone alguien desde afuera. La tentación es armar el texto con un +. No lo hagas.

✗ Así no 
query = "SELECT * FROM productos WHERE nombre = '" + nombre + "'"
cursor.execute(query)

Vos estás escribiendo SQL con las manos del usuario.

✓ Así sí 
query = "SELECT * FROM productos WHERE nombre = %s"
cursor.execute(query, (nombre,))

Vos escribís la consulta y el conector acomoda el dato adentro.

Cómo funciona

%s es un hueco. No es «poné acá un texto»: es «acá va un dato, y lo vas a tratar como dato, pase lo que pase». La tupla del segundo argumento trae los valores que llenan esos huecos, en orden.

Por qué importa tanto

Supongamos que el usuario escribe esto en tu buscador:

Esto tiene nombre

Se llama inyección SQL, y es una de las fallas de seguridad más viejas y más comunes que existen. Lo vas a ver a fondo en otra materia. Por ahora alcanza con la regla: ningún dato que venga de afuera se pega a la consulta con +. Nunca. Va con %s.

Además, te evita errores tontos

Si el dato es...Con +Con %s
RemeraFuncionaFunciona
Camisa D'OrsayRompe: el apóstrofo cierra la comillaFunciona
Un númeroRompe: hay que convertirlo a texto a manoFunciona
Una fechaHay que formatearla vosFunciona
La coma que todos olvidan

(nombre) no es una tupla: es simplemente nombre entre paréntesis. La tupla de un solo elemento se escribe (nombre,), con coma final. Si te olvidás, el error que aparece no menciona la coma por ningún lado — acordate de este cuadro.

Probá
  • Buscá "Gorra" con %s y fetchone().
  • Buscá algo que no exista. ¿Qué devuelve?
  • Probá dos huecos: WHERE precio > %s AND precio < %s con (10000, 30000).
  • Sacale la coma a la tupla de un elemento y mirá el error, para reconocerlo la próxima vez.
06

SELECT, INSERT, UPDATE y DELETE

El SQL de siempre, ahora disparado desde Python

La buena noticia

Las consultas ya las sabés.
Lo nuevo es solamente cómo ejecutarlas desde Python.

SELECT · leer

INSERT · crear

UPDATE · modificar

DELETE · borrar

commit()

commit() significa «confirmo estos cambios». Hasta que no lo llamás, MySQL tiene el cambio anotado en borrador pero no lo guarda de verdad. Si cerrás la conexión sin confirmar, se pierde todo lo que hiciste — y esto no da error, que es lo traicionero: tu programa dice «producto agregado» y en la tabla no hay nada.

Probá (esto hay que verlo una vez)
  • Hacé un INSERT sin commit(). Mirá la tabla en Workbench: no está.
  • Agregá el commit() y repetí. Ahora sí.
  • Después de un UPDATE, imprimí cursor.rowcount: te dice cuántas filas tocó.
  • Hacé un UPDATE con un WHERE que no matchee nada. ¿Da error o da 0?

El problema de repetir código

Donde aparece la necesidad, antes que la solución

Ya sabés hacer las cuatro operaciones. Escribamos entonces el programa completo, con tres funciones nada más:

¿Y si el programa tuviera 30 consultas en vez de 3?

Se repite

30 veces connect() con los mismos cinco datos. 30 cursores. 30 close().

Se olvida

Un commit() que falta en la función 17. Un close() que nunca se llamó. Nadie se da cuenta hasta que falla.

Se rompe

Te mudás de computadora y cambia la contraseña: hay que tocar 30 lugares y no equivocarse en ninguno.

Para pensar
  • ¿Qué parte de esas tres funciones es realmente distinta entre una y otra?
  • Si lo único que cambia es la consulta y los datos... ¿por qué repetimos todo lo demás?
  • ¿Dónde viste antes esta sensación? (Pista: la clase Personaje nació igual.)

¿No sería mejor tener un solo lugar encargado de hablar con la base de datos?

La idea

Un lugar que sepa conectarse y sepa ejecutar una consulta. Todo el resto del programa le pide cosas a ese lugar y no vuelve a ver un connect() en su vida.
Ese lugar va a ser una clase, y la vamos a llamar BasededatosControlador.

Ojo con el orden

Fijate lo que acaba de pasar: primero apareció el problema, después la solución. No empezamos con una clase porque «hay que usar clases». Llegamos a la clase porque el código repetido nos empujó hasta ahí. Así nace casi todo lo que vas a aprender de ahora en adelante.

Paso 2 · Que sepa conectarse

Devuelve la conexión, o devuelve None

Este método siempre contesta algo: si pudo conectarse, te da el objeto conexión; si no pudo, avisa por pantalla y devuelve None. Quien lo llame va a poder preguntar «¿me diste una conexión o no?» antes de seguir. Eso es lo que hace el paso 3.

¿Y el self?

No hay, y no es un olvido. Hasta ahora, los métodos trabajaban sobre un objeto: goku.atacar() necesitaba saber quién es goku. Acá no hay ningún objeto que guardar: no vamos a crear «varios controladores». Hay uno solo y se usa directamente desde la clase, sin instanciar:

conexion = BasededatosControlador.connect()

En Python, la forma prolija de decir «este método no necesita objeto» es ponerle @staticmethod arriba. Funciona sin él, pero con él queda declarado. Poneselo a todos los métodos de esta clase.

Paso 3 · Que sepa ejecutar cualquier consulta

Acá está el truco de toda la guía. Volvé a mirar la tabla del final de la sección 6: las cuatro operaciones se diferencian en tres cosas nada más. Esas tres cosas van a ser los parámetros del método.

ParámetroQué preguntaPara qué sirve
query¿Qué consulta ejecuto?El SQL, con sus %s si hace falta.
params¿Con qué datos?La tupla que llena los huecos. Por defecto, ninguno.
fetchone¿Traigo una fila o todas?True = una sola. Por defecto, todas.
commit¿Esto modifica la base?True en INSERT, UPDATE y DELETE.

Leámoslo línea por línea

connectPide la conexión al otro método. No repite los datos: los pide donde ya están.
if«Si me dieron una conexión de verdad». Si connect() devolvió None, no se intenta nada.
withCrea el cursor y lo cierra solo al terminar el bloque, salga bien o salga mal. Es el mismo with que usás para abrir archivos.
executeLa única línea que realmente habla con MySQL. Si params es None, no pasa nada: la consulta no tenía huecos.
commitSolo confirma si se lo pidieron, y devuelve True para avisar «salió bien».
returnUna fila o todas, según lo que hayan pedido. Un if escrito en una línea.
exceptSi MySQL se queja, lo imprime. El programa no se cae: un error en una consulta no apaga la aplicación entera.
finallyCierra la conexión siempre: haya funcionado, haya fallado, haya habido un return en el medio. Esto es lo que más se olvida a mano.
últimoSi nada salió bien, devuelve algo coherente igual: None o lista vacía, según lo que esperaban. Nunca devuelve sorpresas.
Por qué importa el último return

Quien llama a ejecutar_query quiere recorrer el resultado con un for. Si ante un error devolviéramos None, ese for explotaría. Devolver [] significa «no hubo datos» y el for simplemente no da vueltas. Un buen método falla sin arruinarle el día a quien lo usó.

Lo que acaba de pasar

El resto del programa ya no necesita saber cómo se habla con MySQL. No sabe qué es un cursor, no sabe qué es commit, no conoce la contraseña. Solo pide lo que necesita, con palabras de tu aplicación:

productos = BasededatosControlador.traer_productos()

CapaSabeNo sabe

Fijate en los nombres

traer_productos, buscar_producto, agregar_producto. No se llaman select1, query_a ni funcion2. Los nombres cuentan qué quiere hacer tu aplicación, no cómo lo hace por dentro. Leer la lista de métodos de esta clase debería ser como leer el índice de lo que tu programa puede hacer.

Esto también es POO

Un paso atrás para mirar lo que construimos

No lo dijimos en el camino, pero lo que acabás de hacer es exactamente lo que venís practicando desde la clase 1. Contestá estas preguntas sobre tu propia clase:

Sobre BasededatosControlador
  • ¿Qué es? ¿Un personaje, una cosa del mundo real... o algo distinto?
  • ¿Qué métodos tiene? ¿Cuál usa a cuál?
  • ¿Cuál es su responsabilidad? ¿Podrías decirla en una sola frase?
  • ¿Qué información maneja que el resto del programa no ve?
  • ¿Qué pasa si mañana la base se muda a otro servidor? ¿Cuántos archivos tocás?
Personaje

Representa una cosa: tiene vida, fuerza, nombre. Creás muchos: goku, freezer. Cada uno guarda sus datos.

BasededatosControlador

Representa una responsabilidad: hablar con la base. No hay muchos, hay uno. No guarda datos propios: guarda un saber hacer.

Las dos son clases perfectamente válidas. Una clase no sirve solamente para modelar sustantivos del mundo real: también sirve para juntar en un lugar todo lo que tiene que ver con un mismo asunto.

Encapsulamiento, otra vez

Encapsular también significa esconder detalles
que el resto del programa no necesita conocer.

Cuando aprendiste encapsulamiento, se trataba de proteger atributos: que nadie le ponga vida negativa a un personaje. Es la misma idea, un escalón más arriba. Acá lo que está escondido es todo un procedimiento: la contraseña, el cursor, el commit, el cierre. Quien usa la clase no necesita saber nada de eso, igual que vos no necesitás saber cómo funciona print() por dentro.

La palabra que estamos estrenando

A una clase así se le suele decir servicio o controlador: no representa una cosa, presta un servicio al resto del programa. Es el primer nombre nuevo de una familia que vas a seguir conociendo más adelante en la carrera. Por ahora, con la idea alcanza: un lugar, una responsabilidad.

¿Y si...?

¿Y si mañana la aplicación tuviera que guardar en un archivo de texto en vez de MySQL? Fijate que podrías cambiar todo el interior de ejecutar_query y connect, y el resto del programa seguiría llamando igual a traer_productos() sin enterarse de nada. Eso es lo que hace tan valiosa esta separación.

11

Variables de entorno

Sacar la contraseña del código

¿Qué tiene de malo esto?

Se publica

Subís el proyecto a GitHub para entregarlo y tu contraseña queda a la vista de todos. Y queda en el historial aunque después la borres.

No se comparte

Tu compañero tiene otra contraseña de MySQL. Cada uno tendría que editar el archivo, y alguno lo va a subir cambiado.

No se muda

En tu compu la base está en localhost. En el servidor, no. Mismo código, distintos datos.

Variable de entorno

Es un dato que no vive en tu programa sino en el ambiente donde el programa corre: tu computadora, la de tu compañero, el servidor. El código pregunta «¿cuál es la contraseña acá?» y cada lugar responde la suya.

Con un valor por defecto

El archivo .env

La forma más cómoda de definirlas es un archivo llamado .env (con punto adelante) al lado de tu programa:

1 · instalarpip install python-dotenv — la librería que sabe leer ese archivo.
2 · cargarArriba de todo en tu programa: from dotenv import load_dotenv y después load_dotenv().
3 · usarA partir de ahí, os.getenv("DB_USER") encuentra lo que pusiste en el .env.
4 · ocultarAgregá una línea con .env a tu archivo .gitignore. El .env nunca se sube.
5 · avisarSubí en cambio un .env.example con los nombres y sin los valores, para que el que clone el proyecto sepa qué tiene que completar.

connect(), versión final

Probá
  • Creá el .env, instalá python-dotenv y confirmá que sigue conectando.
  • Cambiá DB_NAME en el .env por una base que no existe. ¿Avisa?
  • Borrá el .env entero. ¿Sigue funcionando? ¿Por qué? (Pista: los valores por defecto.)
  • Imprimí os.getenv("DB_PASSWORD") para ver que lo está leyendo de verdad.
Dónde entra esto más adelante

Cuando tu aplicación deje tu computadora y se vaya a un servidor, nada del código va a cambiar: solo van a cambiar las variables de entorno de ese lugar. Es la razón por la que se hace así en todos lados. Cómo se sube una aplicación a un servidor es tema de otra guía.

Desafíos por nivel

De a uno, y probando cada uno antes de seguir

Todos se resuelven agregando un método a BasededatosControlador y llamándolo desde el menú. Ninguno necesita tocar ejecutar_query.

Nivel 1 · traer_productos()

Devolver todos los productos. Ya está resuelto en la sección 9: escribilo de memoria, sin mirar, y conectalo con la opción 1 del menú.

Pista: no lleva params, no lleva fetchone, no lleva commit.

Nivel 2 · buscar_producto(nombre)

Recibe un nombre y devuelve un solo producto. Opción 2 del menú.

  • ¿Qué devuelve si no lo encuentra? Tu menú tiene que contemplarlo.
  • Mejora: hacelo con LIKE para que «reme» encuentre «Remera». Investigá cómo se arma el % del LIKE junto con el %s del parámetro — no es tan obvio como parece.
Nivel 3 · agregar_producto(nombre, precio)

Inserta un producto nuevo. Opción 3 del menú.

  • Acordate del commit=True.
  • ¿Qué pasa si el usuario escribe "caro" en el precio? Probalo y decidí qué hacer.
  • Validá antes de guardar: nombre no vacío, precio mayor que cero.
Nivel 4 · actualizar_producto(id, nombre, precio)

Modifica un producto existente. Opción 4 del menú.

  • Mostrale primero la lista al usuario para que sepa qué id elegir.
  • Cuidado con el orden de la tupla: los %s del SET van antes que el del WHERE.
  • Si el id no existe, no da error pero no cambia nada. ¿Cómo te enterás? Investigá cursor.rowcount.
Nivel 5 · eliminar_producto(id)

Borra un producto. Opción 5 del menú.

  • Pedí confirmación antes de borrar. Esto no se puede deshacer.
  • Revisá tres veces que el WHERE esté. Probalo con la base de prueba, nunca con datos que te importen.
Nivel 6 · ¿Y si hay dos tablas?

Agregá una tabla clientes (id, nombre, email) y hacé que el programa maneje las dos.

  • Escribí traer_clientes(), agregar_cliente(), etcétera.
  • La pregunta importante: ¿cuánto código nuevo tuviste que escribir para la segunda tabla? ¿Tocaste connect()? ¿Tocaste ejecutar_query()?
  • Si la respuesta fue «no toqué nada de eso», entendiste de qué se trataba la guía.

Para pensar, sin resolverlo todavía: si los métodos de productos y los de clientes empiezan a ser muchos, ¿te seguiría cerrando tenerlos en la misma clase? ¿Qué harías? Guardate la respuesta: es la pregunta con la que arranca la próxima etapa.

¿Cuánto habría que cambiar del controlador?

Nada

Donde la consola hacía print(), la ventana va a hacer etiqueta.setText(). Donde había input(), va a haber campo.text(). La línea del medio es exactamente la misma:

producto = BasededatosControlador.buscar_producto(nombre)
En consola 
nombre = input("Nombre: ")
p = BasededatosControlador.buscar_producto(nombre)
print(p)
En PyQt 
nombre = campo.text()
p = BasededatosControlador.buscar_producto(nombre)
etiqueta.setText(str(p))
La idea que queda

La interfaz no tiene por qué saber
cómo funciona MySQL. Solo pide.

Y funciona en los dos sentidos: la base de datos tampoco sabe que existe una ventana. Por eso el mismo controlador sirve para una app de consola, para una de escritorio y para lo que venga después. Escribiste el controlador una vez; la interfaz podés cambiarla tres veces sin tocarlo.

Si querés adelantarte

Agarrá el mini proyecto de la sección 12 y reemplazá solamente main.py por una ventana PyQt con un campo, un botón y una etiqueta. No toques base_de_datos.py. Si lo lográs sin abrir ese archivo ni una vez, acabás de comprobar vos mismo de qué sirve separar responsabilidades.

Ideas clave

Lo que te tenés que llevar

Las siete ideas de esta guía
  1. Una librería amplía lo que tu programa puede hacer; un conector le permite hablar con otro programa: el servidor de base de datos.
  2. El SQL sigue siendo SQL. Lo que aprendiste en Bases de Datos no cambia: Python se encarga de ejecutarlo y de traer el resultado.
  3. Los datos que vienen de afuera van con %s, nunca pegados con +.
  4. Leer no necesita commit(). Modificar, sí — y si falta, no hay error: simplemente no se guardó nada.
  5. Una clase puede centralizar una responsabilidad, aunque no represente una cosa del mundo real.
  6. Los métodos pueden tener el nombre de las acciones de tu aplicación, no el de las consultas que las resuelven.
  7. La interfaz no necesita conocer la base de datos. Separar responsabilidades es lo que permite que un proyecto crezca sin volverse inmanejable.
