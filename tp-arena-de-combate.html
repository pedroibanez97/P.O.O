Etapa 3 · 🧍

Crear la clase Personaje

Objetivo

Escribir la primera clase del juego: la de arriba, la que van a heredar todos los demás.

01La situación

Abrí juego.py. Vamos a escribir la clase Personaje, que es el molde del que van a salir el héroe y todos los enemigos.

🎯 Antes de escribir +15 XP

¿Por qué conviene empezar por Personaje y no por Jugador?

  • Porque va antes en el alfabeto
  • Porque los demás van a heredar de ella: primero tiene que existir el padre
  • Porque es la clase más larga y difícil

02Paso 1 · los atributos

Arrancamos con lo mínimo: un personaje tiene un nombre y una vida.

🐍 juego.py · versión 1
class Personaje:
    def __init__(self, nombre, vida):
        self.nombre = nombre
        self.vida = vida

La clase

class Personaje: es el molde. Todavía no existe ningún personaje: solo dijimos cómo se fabrican. Se escribe con mayúscula, por convención.

__init__

Es el método que se ejecuta solo, una sola vez: justo cuando escribís Personaje("Aria", 100). Es el momento en que el personaje nace y recibe sus datos. También se lo llama constructor.

self

Quiere decir "yo". self.vida es "mi vida": el personaje hablando de sus propios datos, para no confundirlos con los de otro personaje.

Los atributos

self.nombre y self.vida son la información que cada personaje guarda adentro. Sin el self., el dato no se guarda y después "desaparece". Es el error número uno.

03Paso 2 · que pueda recibir daño

Un personaje al que no le podés pegar no sirve para una arena. Le agregamos su primer método.

🐍 juego.py · versión 2
class Personaje:
    def __init__(self, nombre, vida):
        self.nombre = nombre
        self.vida = vida

    def recibir_danio(self, cantidad):
        self.vida = self.vida - cantidad
📝 Nota sobre los nombres

En la clase 2 lo escribimos recibir_daño, con ñ. Acá lo vamos a escribir recibir_danio, sin ñ. Python acepta las dos, pero sin ñ te evitás problemas al copiar código, al cambiar de teclado o al compartir el archivo. Es exactamente la misma idea, con otro nombre.

🔮 Predicción · antes de ejecutar +15 XP

Si la vida es 100 y el personaje recibe 30 de daño, ¿cuánta vida le queda?

04Paso 3 · que pueda contestar si sigue vivo

Ahora el método más importante de todo el juego, aunque parezca el más chiquito.

🐍 juego.py · versión 3 · la definitiva de esta etapa
class Personaje:
    def __init__(self, nombre, vida):
        self.nombre = nombre
        self.vida = vida

    def recibir_danio(self, cantidad):
        self.vida = self.vida - cantidad

    def esta_vivo(self):
        return self.vida > 0
🔮 Predicción +15 XP

Si la vida es 0, ¿qué devuelve esta_vivo()?

  • True
  • False
  • None
  • Imprime "estás vivo"
📦 print() vs return +20 XP

¿Por qué esta_vivo() usa return y recibir_danio() no?

  • Porque queda más prolijo escribir return
  • Porque esta_vivo() contesta una pregunta que el programa va a usar en un if, y recibir_danio() solo hace un cambio
  • Porque con print() también funcionaría igual
💡 La pregunta que resuelve la duda para siempre

¿Ese resultado lo necesita una persona o lo necesita el programa?
Si lo mira alguien y ahí termina, va print(). Si el programa lo va a guardar, comparar o volver a usar, va return.

⚠️ El problema

¿Qué pasa si recibe más daño que la vida que tiene? La vida queda en negativo. Y un personaje con -400 de vida no existe: el dato miente. Esto ya lo arreglaste una vez, en el ejercicio de la mascota de la clase 1.

06Desafío · arreglalo vos

⚔️ Desafío · completá el código +30 XP

Hacé que la vida nunca quede por debajo de cero.

    def recibir_danio(self, cantidad):
        self.vida = self.vida - cantidad
         self.vida  0:
            self.vida =
💡 Ver pista

Primero restás, y después te fijás si te pasaste. El if va adentro del método (indentado igual que la línea de arriba), no afuera. Y acordate: el arreglo tiene que vivir adentro del objeto, porque es el objeto el que decide cómo cambian sus propios datos. Eso es encapsulación.

🔓 Ver la solución
    def recibir_danio(self, cantidad):
        self.vida = self.vida - cantidad
        if self.vida < 0:
            self.vida = 0   # nunca menos de 0

Ese if es la única razón por la que la vida no queda en negativo. Si lo sacás, el pilar de la encapsulación desaparece: cualquier golpe rompería el dato.

Objetivo

01La situación

Tenemos personajes que pueden recibir daño… pero nadie que se lo haga. Falta con qué pegar.

🧭 Pregunta inicial +15 XP

¿Un Arma es un Personaje? ¿Debería heredar de Personaje?

  • Sí, porque también participa en la pelea
  • No. Es otra cosa distinta: una clase aparte, que no hereda de nadie
  • Sí, pero habría que crear una clase todavía más arriba

02La clase Arma

Le hacemos las dos preguntas de siempre. ¿Qué tiene? Un nombre y un daño. ¿Qué puede hacer? Usarse: entregar cuánto daño hace.

🐍 juego.py · agregalo abajo de Personaje
class Arma:
    def __init__(self, nombre, danio):
        self.nombre = nombre
        self.danio = danio

    def usar(self):
        return self.danio
📝 Nota sobre los nombres

En la clase 2 este método se llamaba atacar(). Acá le decimos usar() porque el arma no ataca sola: la usa alguien. El nombre lo elegís vos; lo que no se negocia es que devuelva el daño.

📦 print() vs return +20 XP

¿Por qué usar() hace return self.danio y no print(self.danio)?

  • Porque así el número se ve mejor en pantalla
  • Porque ese número no es para mirarlo: hay que restárselo a la vida del enemigo
  • Porque return es más rápido que print

02Paso 1 · la herencia y el super()

Un jugador es un personaje: hereda. Y como hereda, no tiene que volver a escribir nombre ni vida.

🐍 juego.py · versión 1
class Jugador(Personaje):
    def __init__(self, nombre, vida):
        super().__init__(nombre, vida)

(Personaje)

Eso es todo lo que hace falta para decir "Jugador ES UN Personaje". Con esa palabra entre paréntesis, el jugador ya tiene recibir_danio() y esta_vivo() sin escribirlos.

super()

Quiere decir "la clase de arriba". Traducido: "Padre, encargate vos de nombre y vida. Yo me ocupo de lo mío." Así cada dato se escribe en un solo lugar del programa.

🐛 Detectá el error +20 XP

Alguien escribió esto y el programa explota en la última línea. ¿Por qué?

class Jugador(Personaje):
    def __init__(self, nombre, vida):
        self.vida = vida        # se olvidó del super()

aria = Jugador("Aria", 100)
print(aria.nombre)
  • Porque Jugador no hereda de Personaje
  • Porque nadie ejecutó el __init__ del padre, así que nombre nunca se guardó
  • Porque print no puede mostrar atributos
⚠️ El síntoma

Si ves un AttributeError: ... has no attribute ..., andá derecho al __init__ del hijo y fijate si está el super(). Casi siempre es eso.

03Paso 2 · el arma entra adentro del jugador

🐍 juego.py · versión 2
class Jugador(Personaje):
    def __init__(self, nombre, vida, arma):
        super().__init__(nombre, vida)
        self.arma = arma
🎁 Toda la novedad de la composición, en una línea

self.arma = arma es la misma línea de siempre: self.algo = algo. Lo único distinto es qué estamos guardando: no es un texto ni un número, es un objeto entero. Un atributo también puede ser otro objeto.

🐍 y así los conectamos
espada = Arma("Espada", 25)
aria = Jugador("Aria", 100, espada)

Primero fabricamos el arma. Después fabricamos al jugador pasándole esa arma. El objeto espada entra adentro del objeto aria.

🔮 Predicción +20 XP

¿Qué imprime print(aria.arma.nombre)?

🔎 El punto se lee "de", de derecha a izquierda

aria.arma.nombre = "el nombre del arma de Aria". Cada punto es un paso más adentro. Si te perdés en una línea larga con muchos puntos, leela así y se ordena sola.

04Paso 3 · que ataque (dos objetos colaborando)

class Jugador(Personaje):
    def __init__(self, nombre, vida, arma):
        super().__init__(nombre, vida)
        self.arma = arma

    def atacar(self):
        return self.arma.usar()
La línea más importante de la etapa El jugador no sabe cuánto daño hace.
Le pregunta al arma.
🧩 Entender la línea +20 XP

En return self.arma.usar(), ¿cuántos objetos participan y qué hace cada uno?

  • Uno: el jugador calcula el daño él solo
  • Dos: el jugador le pide el daño a su arma, y devuelve esa respuesta
  • Tres: el jugador, el arma y el enemigo
🧩 ¿Y por qué esto es tan útil? Cambiar de arma
hacha = Arma("Hacha", 40)
aria.arma = hacha

Objetivo

Que todos los enemigos entiendan atacar(), pero que cada uno conteste a su manera.

01La situación

Una idea es esta. ¿Qué problema tiene?

        return self.danio + 15
🐍 el goblin pega normal

    def atacar(self):
        return self.danio

Fijate qué corto quedó. Ninguno de los dos escribe __init__: lo heredan de Enemigo tal cual, porque no agregan ningún atributo nuevo. Solo cambian cómo responden a una orden.

atacar()
danio

Cero. El for no sabe ni le importa quién es cada uno: cada objeto sabe cómo responder. Y si mañana agregás un Fantasma, no tocás una sola línea del for.

🤔 Una pregunta para pensar: ¿hacía falta escribir atacar() en Goblin?

Etapa 11 · 🎮

Objetivo

Ponerle al sistema que construiste una forma de usarlo. Y armar el programa completo.

01La situación

⚠️ Antes que nada, que quede claro

El menú no es el objetivo del trabajo práctico. Es solamente la forma de usar el sistema que construiste. Lo importante ya está hecho: las clases, la herencia, la composición, el return y el polimorfismo. El menú son if y elif, y eso ya lo sabías hacer desde antes de POO.

Igual, sin menú el juego no se juega: se ejecuta y se termina solo. Vamos a darle a la persona la posibilidad de decidir.

# ===== ARENA DE COMBATE =====
# Trabajo práctico integrador de POO

class Personaje:
    def __init__(self, nombre, vida):
        self.nombre = nombre
        self.vida = vida
        self.vida_maxima = vida

    def recibir_danio(self, cantidad):
        self.vida = self.vida - cantidad
        if self.vida < 0:
            self.vida = 0

    def esta_vivo(self):
        return self.vida > 0

    def mostrar_info(self):
        print(self.nombre, "- Vida:", self.vida, "/", self.vida_maxima)


class Arma:
    def __init__(self, nombre, danio):
        self.nombre = nombre
        self.danio = danio

    def usar(self):
        return self.danio


class Pocion:
    def __init__(self, nombre, cura):
        self.nombre = nombre
        self.cura = cura

    def usar(self):
        return self.cura


class Jugador(Personaje):
    def __init__(self, nombre, vida, arma):
        super().__init__(nombre, vida)
        self.arma = arma
        self.nivel = 1
        self.experiencia = 0

    def atacar(self):
        return self.arma.usar()

    def curarse(self, pocion):
        self.vida = self.vida + pocion.usar()
        if self.vida > self.vida_maxima:
            self.vida = self.vida_maxima

    def ganar_experiencia(self, cantidad):
        self.experiencia = self.experiencia + cantidad
        print(self.nombre, "ganó", cantidad, "de experiencia")
        if self.experiencia >= 100:
            self.subir_nivel()

    def subir_nivel(self):
        self.nivel = self.nivel + 1
        self.experiencia = self.experiencia - 100
        self.vida_maxima = self.vida_maxima + 20
        self.vida = self.vida_maxima
        print(self.nombre, "subió al nivel", self.nivel)


class Enemigo(Personaje):
    def __init__(self, nombre, vida, danio):
        super().__init__(nombre, vida)
        self.danio = danio

    def atacar(self):
        return self.danio


class Goblin(Enemigo):
    def atacar(self):
        return self.danio          # igual que el padre: podría no escribirse


class Dragon(Enemigo):
    def atacar(self):
        return self.danio + 15     # el dragón pega más fuerte


# ===== creamos los objetos =====
espada = Arma("Espada", 25)
pocion = Pocion("Poción chica", 30)
heroe = Jugador("Aria", 150, espada)     # 150 de vida: el dragón pega fuerte
enemigo = Dragon("Dragón rojo", 90, 20)  # 20 + 15 = 35 de daño por golpe

# ===== el menú =====
while True:
    print()
    print("=== ARENA DE COMBATE ===")
    print("1. Ver información")
    print("2. Atacar")
    print("3. Usar poción")
    print("4. Ver experiencia")
    print("5. Salir")
    opcion = input("Elegí una opción: ")

    if opcion == "1":
        heroe.mostrar_info()
        enemigo.mostrar_info()

    elif opcion == "2":
        danio = heroe.atacar()
        enemigo.recibir_danio(danio)
        print(heroe.nombre, "atacó con", heroe.arma.nombre, "e hizo", danio, "de daño")

        if enemigo.esta_vivo():
            golpe = enemigo.atacar()
            heroe.recibir_danio(golpe)
            print(enemigo.nombre, "contraatacó e hizo", golpe, "de daño")
        else:
            print(enemigo.nombre, "fue derrotado")
            heroe.ganar_experiencia(50)

    elif opcion == "3":
        heroe.curarse(pocion)
        print(heroe.nombre, "usó", pocion.nombre, "- Vida:", heroe.vida)

    elif opcion == "4":
        print("Nivel:", heroe.nivel, "- Experiencia:", heroe.experiencia, "/ 100")

    elif opcion == "5":
        print("¡Hasta la próxima!")
        break

    else:
        print("Esa opción no existe")

    if not heroe.esta_vivo():
        print("GAME OVER")
        break

05Cómo se evalúa

Se evalúa principalmente el razonamiento y la comprensión, no la cantidad de funcionalidades. Un juego chiquito que entendés a fondo vale más que uno enorme que no sabés explicar.

Qué se miraLo esperado
Identificación de objetosEncontró los objetos del problema y no convirtió en clase cualquier cosa que se le ocurrió.
Diseño de clasesLo común está arriba, lo específico abajo. Cada clase tiene un motivo para existir.
Atributos y métodosLos atributos son datos y están en la clase correcta; los métodos son acciones y hacen una cosa cada uno.
HerenciaSe usa donde se puede decir "ES UN", y no para ahorrar líneas porque sí.
Uso de super()El hijo no repite los atributos del padre. Puede explicar qué pasa si lo saca.
ComposiciónHay al menos un objeto adentro de otro, y sabe justificar por qué ahí no iba herencia.
PolimorfismoDistintos objetos responden al mismo método a su manera, y el código que los usa no tiene cadenas de if.
Uso de returnDevuelve cuando el programa necesita el valor; imprime cuando lo lee una persona. Puede explicar cada caso.
FuncionamientoEl programa corre sin errores y hace lo que dice que hace.
Explicar las decisionesLo que más pesa. Puede contar por qué diseñó así y qué otra opción había.
Prolijidad y mejorasNombres claros, código ordenado, y una idea concreta de cómo seguiría.
